# Git 브랜치 전략 비교

## 트렁크 기반 개발
모든 개발자가 하나의 main 브랜치에 자주 작게 통합한다.
브랜치 수명이 하루 이틀로 짧아 병합 충돌이 적다.
미완성 기능은 기능 플래그로 감춰 두고 배포한다.
자동 테스트가 탄탄한 팀에 알맞다.

## Git Flow
main과 develop 브랜치를 분리하고 feature, release, hotfix 브랜치를 따로 둔다.
릴리스 주기가 길고 여러 버전을 동시에 유지보수해야 하는 제품에 어울린다.
브랜치가 많아 관리가 복잡하고 병합 충돌이 자주 생기는 것이 단점이다.

## GitHub Flow
main은 항상 배포 가능한 상태로 유지하고, 작업은 기능 브랜치에서 하고 풀 리퀘스트로 리뷰를 거쳐 병합한다.
단순해서 웹 서비스처럼 지속 배포하는 팀에 잘 맞는다.

## 병합 방식
머지 커밋은 이력을 그대로 보존하지만 그래프가 복잡해진다.
리베이스는 이력을 일직선으로 정리하지만 공유된 브랜치에 쓰면 다른 사람의 이력이 꼬인다.
스쿼시 병합은 브랜치의 커밋을 하나로 합쳐 main 이력을 깔끔하게 유지한다.

## 충돌 해결
충돌은 같은 줄을 두 브랜치가 다르게 고쳤을 때 생긴다.
충돌 표시를 열어 어느 쪽을 남길지 정하고 다시 커밋한다.
