0. 한 줄 요약
RAG가 "질문 시점에 문서를 찾아오는" 방식이라면, LLM Wiki는 "문서가 들어오는 시점에 지식을 정리·연결해두는" 방식이다. 발표자는 자신의 회사에서 이를 Knowledge Context 라 이름 짓고, Obsidian + Git + RAG + 사람 개입 승인 프로세스로 운영한다.

1. 출발 — "왜 AI에게 매번 같은 설명을 반복해야 하는가"
발표자가 명시한 4가지 흩어진 지식의 형태:

채팅 세션의 좋은 답변 — 메모장에 복사해두지 않으면 사라짐
회의록 — 막내가 열심히 타이핑하지 않으면 결정과 근거가 분리됨
개인 메모 — 메신저로 강제 공유하지 않으면 팀이 볼 수 없는 암묵지 로 남음
반복 설명 — 사람도 AI도 매번 맥락을 다시 이해하는 비용을 치름
"지식이 흩어져 있으면 사람도 AI도 매번 찾거나, 맥락을 이해하는 비용을 치러야만 했습니다."

2. RAG의 한계 (영상 06:29 챕터)
RAG는 "뭐가 들어왔는지 모르지만 일단 때려 박는" 식의 문서 저장소.
시스템적으로 설계가 쉬워 빠르게 적용 가능.
그러나 결국 쓰레기 산 이 된다 — 문서 품질 보존이 매우 어려움.
질문 시점에 검색만 잘 되면 되지만, 들어오는 문서의 맥락·연결·중복 여부 가 관리되지 않음.
3. LLM Wiki의 핵심 구조 (영상 07:47 챕터)
원조 개념: Andrej Karpathy 가 제안한 LLM Wiki (혹은 Second Brain 으로도 불림)
발표자의 회사명 표현: Knowledge Context (날리지 컨텍스트)
핵심 차이:
RAG = 질문 → 검색 → 응답 의 lazy 방식
LLM Wiki = 문서 진입 → 정리 → 위키 자체가 관리 의 eager 방식
위키는 "이 문서가 여기에 들어와 있어요" 라는 정보를 자체적으로 관리 함
새 정보가 위키에 있는지 없는지를 위키 자체가 판단 함
4. LLM Wiki가 쓰레기산이 되지 않으려면 (영상 11:31 챕터)
발표자가 강조한 핵심 — 문서가 그냥 쌓이기만 하면 LLM Wiki도 RAG와 똑같은 운명. 그래서 Obsidian + Git + RAG + 사람 승인 의 조합이 필요하다.

5. 실제 구성 방식 (영상 13:17 챕터, 발표의 핵심)
구성요소	역할
Obsidian	LLM Wiki의 프론트엔드/저장소 — 마크다운 파일 + 양방향 링크 + 그래프 뷰. 비개발자도 사용 가능
Git	동기화 + 버전 관리 시스템. Obsidian의 마크다운 폴더를 Git 리포지토리로 관리하면 다중 인원 동기화 가능
RAG (재연결)	LLM Wiki가 충분히 커지면 그 안에서의 검색 을 위해 RAG를 다시 얹음 (§6 참조)
사람 개입 승인	새 문서/수정 사항을 위키에 반영하기 전 사람이 검토하고 머지 — Git PR 패턴과 유사
Claude Code / Codex	LLM Wiki를 연결한 코딩 에이전트 — Obsidian CLI 도구를 활용
Obsidian Skill	발표 이틀 전(2026-05-17경) Anthropic CEO가 Obsidian Skill을 공개. LLM Wiki ↔ Obsidian 연동이 더 편리해짐
환경 특성: 비개발자 + 개발자가 섞인 작은 스타트업 에서 운영.

6. LLM Wiki에 RAG를 다시 연결한 이유 (영상 23:43 챕터)
LLM Wiki가 커지면 위키 자체 안의 검색 도 필요해진다.
이때 RAG를 위키의 검색 엔진 으로 다시 얹는다 — RAG vs LLM Wiki가 경쟁 이 아니라 계층 임을 보여줌.
구조: 사용자/AI 질문 → LLM Wiki (1차 정리/연결) → RAG (검색) → 응답
7. AI에게 어디까지 맡길 것인가 (영상 30:13 챕터)
자동화 vs 사람 개입의 경계 — 발표자는 사람 개입 승인 프로세스 를 의도적으로 남겨둠
위키에 새 문서가 들어가는 순간, 누구의 책임으로 어떤 카테고리에 들어갈지 는 사람이 결정
AI는 정리 보조 + 검색 보조 역할
8. 영상에서 도출된 실무 통찰
RAG는 시작점이지 종착점이 아니다 — 쓰레기 산이 되기 전에 LLM Wiki로 진화시켜야.
Obsidian의 강점: 마크다운 + 양방향 링크 + CLI 도구 + 그래프 뷰가 LLM Wiki 운영에 최적.
Git as Sync: 별도 DB 없이 Git 자체가 동기화 + 이력 + PR 승인 까지 해결.
승인 프로세스 = 품질 게이트: 모든 자동화는 사람이 한 번 보고 머지 하는 단계를 거침.
LLM Wiki + RAG는 양립: 위키 자체 검색에 RAG 사용 → 두 패러다임은 계층적으로 결합 가능.
