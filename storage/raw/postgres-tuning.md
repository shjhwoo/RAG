# PostgreSQL 쿼리 성능 튜닝 노트

## 실행 계획부터 본다
느린 쿼리를 만나면 감으로 인덱스를 추가하기 전에 EXPLAIN (ANALYZE, BUFFERS)로 실행 계획을 먼저 확인한다.
실행 계획에서 Seq Scan이 큰 테이블에 나타나고 필터로 버려지는 행이 많다면 인덱스 후보다.
추정 행 수와 실제 행 수가 크게 어긋나면 통계가 오래된 것이므로 ANALYZE를 다시 돌린다.

## 인덱스 종류와 선택
가장 기본은 B-tree 인덱스이며 동등 비교와 범위 조건, 정렬에 쓰인다.
여러 컬럼을 함께 거는 복합 인덱스는 컬럼 순서가 중요하다. 선택도가 높고 자주 쓰는 조건을 앞에 둔다.
조건을 만족하는 일부 행만 색인하는 부분 인덱스는 인덱스 크기를 크게 줄여 준다.
JSONB나 배열 컬럼에는 GIN 인덱스를 쓴다.
인덱스는 읽기를 빠르게 하는 대신 쓰기 비용과 저장 공간을 늘리므로 쓰지 않는 인덱스는 정리한다.

## 조인과 통계
중첩 루프 조인은 한쪽이 작을 때, 해시 조인은 큰 테이블끼리 동등 조인할 때 유리하다.
work_mem이 너무 작으면 정렬과 해시가 디스크로 넘어가 느려진다.
autovacuum이 밀리면 죽은 튜플이 쌓여 테이블이 부풀고 스캔이 느려진다.

## 흔한 실수
WHERE 절에서 컬럼에 함수를 씌우면 일반 인덱스를 타지 못한다. 필요하면 함수 기반 인덱스를 만든다.
OFFSET이 큰 페이지네이션은 앞의 행을 전부 읽고 버리므로 키셋 페이지네이션으로 바꾼다.
SELECT *는 커버링 인덱스의 이점을 없앤다. 필요한 컬럼만 고른다.
